# From an on-chain question to a working Solana app

Arete is a toolkit for building on Solana **with an AI agent**. You describe
what you want to know or build. Your agent finds the right on-chain programs,
checks live data to confirm it has what you need, and installs ready-made,
fully typed code into your project.

You can start with nothing but a question. You don't need to know a program ID,
an account layout, a view name, or an endpoint first. Finding those is the
agent's job.

1. **Explore.** Your agent searches the Arete catalog for programs and live
   views that match what you asked, then connects and looks at real data. It
   does this through MCP, the standard way agents plug into outside tools.
2. **Shape.** If an existing view already has the data your app needs, use it.
   If the catalog doesn't have one, define a focused view that does.
3. **Ship.** Your choices are written to `arete.toml`, pinned to exact versions
   in `arete.lock`, and turned into generated code with stable types your app
   can build on.

## Start with one prompt

Open your project in a coding agent and paste this:

<CopyPrompt>
Read https://docs.arete.run/agent.md and follow it to set up Arete in this
project. Verify the setup, and simply explain what Arete is capable of.
</CopyPrompt>

That one page tells the agent everything it needs: how to install the `a4`
command-line tool, set up your project, check that everything works, and find
its way around the catalog. Behind the scenes, `a4 init` installs the Arete
skills and connects both MCP servers for whichever agent you're using.

[See the manual equivalent →](/using-stacks/quickstart/)

## Programs are the foundation

A Solana **program** is an app that lives on-chain. Other chains call these
smart contracts. For every program it supports, Arete generates a **Program
SDK**: code your app (or your agent) uses to read that program's data and send
it transactions, without anyone decoding bytes by hand.

What's inside depends on the program and the language you pick, but the layout
is always the same:

| Surface | What it gives you |
| --- | --- |
| **Accounts** | The program's on-chain data as typed objects, matched to the exact release you installed |
| **PDAs and addresses** | The addresses the program uses, worked out for you instead of copied seed logic |
| **Raw instructions** | Low-level builders that mirror the program's own interface one-to-one |
| **Operations and flows** | Higher-level actions shaped like what your app does, including ones that span several instructions or transactions |
| **Transactions** | Local signing, inspection before sending, submission, confirmation, and clear outcomes when something fails |
| **Chain** | General Solana reads for anything outside the program's own accounts |

[Understand Program SDKs →](/using-programs/overview/)

## Add live views where they help

A program's accounts are the raw material. A **live view** is that data
arranged the way an app wants to read it, and kept current as the chain
changes: open positions, active rounds, rankings, totals, filtered activity. A
view can draw on one program or several. Views are optional. Add them when
reading accounts one by one stops being enough.

A **stack** is the installable bundle: a set of live views plus the Program
SDKs they depend on. Your app installs the stack. How those views are grouped
or hosted behind the scenes is not something it needs to know.

[Programs, views, and stacks →](/concepts/programs-views-stacks/)

## Typed all the way into your application

Everything you install, stacks and standalone programs alike, comes together in
one session object inside your app. Each package lists the languages it has
been verified for, so choose from TypeScript, React, Rust, or Python

## Exact, inspectable dependencies

`arete.toml` lists what your project wants to use. `arete.lock` records exactly
what `a4 install` resolved that to: the precise program, stack, artifact, and
generated-package identities. Between them, anyone (or any agent) can rebuild
the same project later.

Generated files are stamped with where they came from. When something needs to
change, regenerate them instead of editing them by hand.
