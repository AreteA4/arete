Arete is a toolkit for discovering and using Solana programs without rebuilding
the same decoding, RPC, transaction, and indexing infrastructure for every
application.

It is designed for agents first. A coding agent can translate a goal into exact
programs and capabilities, inspect their current descriptors, explore deployed
live data through MCP, and generate the SDK your application will use.

## Start from intent

A normal Arete workflow begins with what you want to accomplish:

- “Show me active liquidity pools.”
- “Watch new token launches and summarize them.”
- “Read this multisig and prepare a proposal.”
- “Build a deposit transaction for this position.”

The catalog maps that intent to programs and reports which modes are available:

| Mode        | What it means                                         |
| ----------- | ----------------------------------------------------- |
| `read`      | Typed program-account reads and generic Solana state  |
| `build`     | Instructions, transactions, and higher-level flows    |
| `subscribe` | Current-state and live views from a hosted deployment |

Catalog results are discovery information. Before writing code, the agent opens
the exact program or stack descriptor to learn the real account names, views,
SDK targets, authentication requirements, and install command.

## Every program becomes an application interface

The base unit in Arete is a **program**. A generated Program SDK can include:

- typed account schemas and release-pinned account readers;
- PDA and known-address helpers;
- pure, offline instruction builders;
- application-shaped operations and multi-step flows;
- transaction inspection and execution through a locally signing wallet; and
- generated constants, defaults, calculations, and error metadata where the
  program package defines them.

You do not need a live stack to use a Program SDK. Programs can be installed
and composed independently.

## Views add application-shaped live data

Program accounts are not always the shape an application wants to consume.
A product might need a joined position, a sorted leaderboard, recent activity,
or an aggregate assembled from several accounts and instructions.

A **view** is that application-facing read model. Views can provide a point-in-
time result and, when hosted over WebSocket, continuous updates. They may use
one program or combine data from several programs.

Agents can inspect and query deployed views through MCP before any application
code exists. This makes exploration part of the development loop rather than a
separate indexing project.

## Stacks package a complete capability

A **stack** is an installable composition of:

- one or more Program SDKs;
- selected live views;
- generated application operations and helpers; and
- the bindings required to use the available hosted capabilities.

The fact that several views may share a hosted runtime is an operational
detail. The application-facing model is the composition it installs.

For exact terminology, see [Programs, views, and stacks](/concepts/programs-views-stacks/).

## One generated session

Applications can install several stacks and standalone programs into one
session. The session provides stable access to:

- `session.stacks` for each installed stack;
- `session.programs` for canonical program interfaces;
- `session.chain` for generic Solana reads; and
- transaction preparation and execution shared across the application.

The generated code carries exact identities and connection descriptors. Your
application should not construct hosted endpoints or guess schemas itself.

## Explore before you build

The fastest way to understand Arete is to ask an agent a real question. The
agent can search the catalog, connect to an existing live view, and explain
what the data contains. When the result becomes part of a product, install the
same exact capability into the project and build against its generated types.

## What Arete does not hide

Arete removes repetitive integration work, but preserves important boundaries:

- generated descriptors and types are the authority for the installed release;
- reading, preparing, inspecting, signing, and submitting are different actions;
- wallets sign locally and Arete never receives private keys;
- Program Read, generic chain reads, live views, and transaction submission are
  independent capabilities; and
- a catalog entry may be known without every delivery mode being available.

This lets agents automate the mechanical work without fabricating capabilities
or crossing transaction and deployment boundaries silently.
