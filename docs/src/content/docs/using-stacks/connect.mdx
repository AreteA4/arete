title: Connect to Live Views
description: Find a stack with live data, then use its generated SDK to fetch current results and stream updates.
---

A live view is data from one or more programs, arranged the way your app wants
it and kept current for you. Reach for one when reading accounts by address
stops being enough, because you need collections, joins, totals, rankings,
recent activity, or a continuous stream of updates.

## Find a subscribe-ready stack

Search the catalog each time. Example deployments come and go, so don't build
on a fixed one:

```bash
a4 explore catalog --query "<intent>" --kind stack --mode subscribe --json
a4 explore catalog stack <slug> --json
```

The exact descriptor lists the stack's views, programs, sign-in requirements,
connection details, verified SDK targets, and install command. If the search
returns nothing that is subscribe-ready, stop there. Don't construct a URL from
a package name.

## Explore it before writing code

The quickest way to check a view is through MCP. Ask your agent to inspect the
view schema, connect, take a small bounded sample, and tell you whether the data
answers your application's question.

[Explore on-chain with MCP →](/agent-skills/explore-on-chain/)

## Install the stack

```bash
a4 install stack <slug> --ts
```

Use the target and command the descriptor gives you. The dependency you asked
for is saved in `arete.toml`, and the exact composition and package identities
go into `arete.lock`.

Install the TypeScript runtime when needed:

```bash
npm install @usearete/sdk
```

For React:

```bash
npm install @usearete/react @usearete/sdk zod
```

## TypeScript session

Use the generated import and names printed by `a4 install`:

```ts
import { createSession } from "@usearete/sdk";
import { MY_STACK } from "./generated/my-stack";

const session = await createSession(
  { stacks: { app: MY_STACK } },
  { auth: { publishableKey: process.env.ARETE_PUBLISHABLE_KEY } },
);

const current = await session.stacks.app.views.Position.list.get({ take: 20 });

for await (const update of session.stacks.app.views.Position.list.watch({
  take: 20,
})) {
  if (update.type === "upsert") {
    console.log(update.data);
  } else {
    console.log(update.type, update.key);
  }
}
```

`MY_STACK`, `Position`, and the query options shown here are placeholders. The
generated declarations in your installed package have the real names.

The stack already contains its default endpoints. Override them only when you
deliberately want a local or alternate connection.

## React

```tsx
import { AreteProvider, useArete } from "@usearete/react";
import { MY_STACK } from "./generated/my-stack";

function Positions() {
  const arete = useArete(MY_STACK);
  const positions = arete.views.Position.list.use({ take: 20 });

  if (arete.status === "error") {
    return <button onClick={() => void arete.retry()}>Reconnect</button>;
  }
  if (positions.status !== "ready") return <p>Loading…</p>;
  if (positions.isEmpty) return <p>No matching positions.</p>;

  return <pre>{JSON.stringify(positions.data, null, 2)}</pre>;
}

export default function App() {
  return (
    <AreteProvider
      stack={MY_STACK}
      auth={{ publishableKey: import.meta.env.VITE_ARETE_PUBLISHABLE_KEY }}
    >
      <Positions />
    </AreteProvider>
  );
}
```

Reading hosted data may require you to sign in, but it never requires a
wallet. In your interface, treat connecting, ready but empty, ready with data,
refreshing, validation failure, and connection failure as different states.

## Point-in-time versus live

Generated view clients commonly expose:

| Method            | Use                                                           |
| ----------------- | ------------------------------------------------------------- |
| `.get(...)`       | Fetch a point-in-time result                                  |
| `.getOne(...)`    | Fetch the first result of a list view                         |
| `.use(...)`       | Consume merged entities as an async iterable or React hook    |
| `.watch(...)`     | Consume the full update taxonomy                              |
| `.watchRich(...)` | Consume updates with before/after information where supported |
| `.getSync(...)`   | Read the already-active local subscription state              |

The exact methods vary by language and by view. Two things to remember: a
point-in-time request is not a live subscription, and `getSync` never makes a
network request.

## Query semantics

Keys, filters, partitions, pagination, and bounded snapshot windows all count
as part of a subscription's identity. Two queries that normalize to the same
thing can share one connection. Queries with different windows stay
independent.

When an entity drops out of one filtered query, it hasn't necessarily been
deleted everywhere. Keep the update types the generated SDK gives you, so your
application state stays correct.

[Filtering and query windows →](/using-stacks/filtering-feeds/)

## Programs packaged by a stack

A generated stack can also include its Program SDKs. They appear under the
stack and, where identities permit, the session's canonical program surface:

```ts
session.stacks.app.programs.myProgram;
session.programs.myProgram;
```

Use those program clients when you need the authoritative account data or want
to build a transaction. Use views when you want data that is already shaped and
maintained for your app.

## Independent hosted capabilities

Live queries, Program Read, generic chain reads, and transactions each have
their own descriptor and their own authentication scope. Don't reuse a WebSocket
or HTTP query URL as a program, chain, or transaction endpoint.

For transaction execution, the wallet signs locally and the connected client
selects the correct transaction transport per invocation.

## Other languages

Use `a4 install stack <slug> --rust` or `--python` only when the descriptor
verifies the target. Continue with the [Rust SDK](/sdks/rust/) or
[Python SDK](/sdks/python/) for language-specific patterns.
