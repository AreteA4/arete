Live views are maintained, application-shaped state over one or more programs.
Use them when account-by-address reads are not enough: collections, joins,
aggregates, rankings, recent activity, or continuous updates.

## Find a subscribe-ready stack

Search dynamically instead of relying on a fixed example deployment:

```bash
a4 explore catalog --query "<intent>" --kind stack --mode subscribe --json
a4 explore catalog stack <slug> --json
```

The exact descriptor identifies selected views, programs, authentication,
bindings, verified SDK targets, and the install command. If search returns no
subscribe-ready result, do not construct a URL from a package name.

## Explore it before writing code

The quickest validation is through MCP. Ask your agent to inspect the view
schema, connect, take a bounded sample, and explain whether the data answers the
application question.

[Explore on-chain with MCP →](/agent-skills/explore-on-chain/)

## Install the stack

```bash
a4 install stack <slug> --ts
```

Use the descriptor's target and command. The saved dependency is recorded in
`arete.toml`; exact composition and package identities are recorded in
`arete.lock`.

Install the TypeScript runtime when needed:

```bash
npm install @usearete/sdk
```

For React:

```bash
npm install @usearete/react @usearete/sdk zod
```

## TypeScript session

Use the generated import and names printed by `a4 install`:

```ts
import { createSession } from "@usearete/sdk";
import { MY_STACK } from "./generated/my-stack";

const session = await createSession(
  { stacks: { app: MY_STACK } },
  { auth: { publishableKey: process.env.ARETE_PUBLISHABLE_KEY } },
);

const current = await session.stacks.app.views.Position.list.get({ take: 20 });

for await (const update of session.stacks.app.views.Position.list.watch({
  take: 20,
})) {
  if (update.type === "upsert") {
    console.log(update.data);
  } else {
    console.log(update.type, update.key);
  }
}
```

`MY_STACK`, `Position`, and the available query options are placeholders. Use
the generated declarations for the installed package.

The stack embeds its default endpoints. Override them only when intentionally
connecting to a local or alternate binding.

## React

```tsx
import { AreteProvider, useArete } from "@usearete/react";
import { MY_STACK } from "./generated/my-stack";

function Positions() {
  const arete = useArete(MY_STACK);
  const positions = arete.views.Position.list.use({ take: 20 });

  if (arete.status === "error") {
    return <button onClick={() => void arete.retry()}>Reconnect</button>;
  }
  if (positions.status !== "ready") return <p>Loading…</p>;
  if (positions.isEmpty) return <p>No matching positions.</p>;

  return <pre>{JSON.stringify(positions.data, null, 2)}</pre>;
}

export default function App() {
  return (
    <AreteProvider
      stack={MY_STACK}
      auth={{ publishableKey: import.meta.env.VITE_ARETE_PUBLISHABLE_KEY }}
    >
      <Positions />
    </AreteProvider>
  );
}
```

Read-only hosted access may require authentication but does not require a
wallet. Treat connecting, ready-empty, ready-with-data, refreshing, validation
failure, and connection failure as different UI states.

## Point-in-time versus live

Generated view clients commonly expose:

| Method            | Use                                                           |
| ----------------- | ------------------------------------------------------------- |
| `.get(...)`       | Fetch a point-in-time result                                  |
| `.getOne(...)`    | Fetch the first result of a list view                         |
| `.use(...)`       | Consume merged entities as an async iterable or React hook    |
| `.watch(...)`     | Consume the full update taxonomy                              |
| `.watchRich(...)` | Consume updates with before/after information where supported |
| `.getSync(...)`   | Read the already-active local subscription state              |

Exact methods vary by language and view. A point-in-time request is not a live
subscription, and `getSync` does not perform a network fetch.

## Query semantics

Keys, filters, partitions, pagination, and bounded snapshot windows are part of
the subscription identity. Equivalent normalized queries can share one
connection; different windows remain independent.

An entity leaving one filtered query is not necessarily deleted globally.
Preserve the generated update taxonomy so application state remains correct.

[Filtering and query windows →](/using-stacks/filtering-feeds/)

## Programs packaged by a stack

A generated stack can also include its Program SDKs. They appear under the
stack and, where identities permit, the session's canonical program surface:

```ts
session.stacks.app.programs.myProgram;
session.programs.myProgram;
```

Use those program clients for authoritative account reads and transaction
construction. Use views for maintained application read models.

## Independent hosted capabilities

Live queries, Program Read, generic chain reads, and transactions have separate
descriptors and authentication scopes. Do not reuse a WebSocket or HTTP query
URL as a program, chain, or transaction endpoint.

For transaction execution, the wallet signs locally and the connected client
selects the correct transaction transport per invocation.

## Other languages

Use `a4 install stack <slug> --rust` or `--python` only when the descriptor
verifies the target. Continue with the [Rust SDK](/sdks/rust/) or
