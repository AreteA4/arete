---
title: How Arete Works
description: How discovery, generated SDKs, hosted capabilities, and live views fit together.
---

Arete separates portable program and view definitions from the hosted services
that deliver them. This gives applications exact generated interfaces without
making infrastructure topology part of the public API.

## The complete path

```text
Intent
  ↓
Catalog and knowledge
  ↓
Exact program or stack descriptor
  ↓
arete.toml + arete.lock
  ↓
Generated SDK
  ↓
Application session
  ├── Program Read
  ├── Generic chain reads
  ├── Live view queries and subscriptions
  └── Transaction inspection and submission
```

Each boundary is inspectable. Agents use the catalog for discovery, exact
descriptors for capability truth, and generated code for application APIs.

## Discovery: find capabilities from intent

The catalog records programs and stacks together with concepts, categories,
verified SDK targets, and delivery modes:

- `read` — typed program accounts and generic chain state;
- `build` — instructions, transactions, and flows; and
- `subscribe` — hosted current-state and live views.

Search results are not SDK schemas. After finding a candidate, `a4 explore`
opens its pinned descriptor. That descriptor is the source of truth for the
specific version an application can install.

## Installation: turn discovery into a project dependency

`a4 install` records human-readable intent in `arete.toml` and exact resolution
in `arete.lock`. It then generates language-specific code and provenance for
the whole dependency graph.

This means a project can express:

- standalone Program SDKs;
- stacks containing live views and their programs;
- multiple SDK targets; and
- local or workspace-authored artifacts where appropriate.

Generation is transactional: outputs and the lockfile are committed together
after the complete graph validates.

## Program Read: exact decoded accounts

Program Read fetches and decodes accounts for an exact published program
release. The generated client already knows the schema and release identity.
Use this surface when you have an address and want current program-owned state.

It is independent of live views. A standalone Program SDK can be read-ready
without any deployed stack.

## Chain gateway: generic state and transactions

The Solana gateway provides capabilities that are not tied to one program
account schema:

- generic account, balance, mint, rent, and clock reads;
- transaction blockhash, fee, and simulation support; and
- submission and confirmation for locally signed transactions.

Read and transaction scopes are independent. The wallet compiles and signs
locally; Arete never receives the private key.

Hosted packages carry explicit gateway descriptors. Clients do not derive the
gateway from a stack's WebSocket URL.

## Live views: maintained application state

Live views transform account and instruction updates into application-facing
entities. A view can provide keyed state, a collection, or a bounded filtered
and sorted window.

Clients can:

- fetch a point-in-time result over HTTP;
- subscribe to updates over WebSocket;
- apply server-side keys, filters, partitions, and limits; and
- reconcile application state after a confirmed transaction.

View subscriptions use an explicit update taxonomy. A row can be added or
changed, leave one query while continuing to exist, or be deleted globally.
Use the generated SDK rather than reducing every update to an upsert/delete
pair.

## MCP: the exploratory client

The local Arete MCP server exposes catalog discovery and live-view operations
to an agent. It can connect to a deployed stack, maintain a bounded cache for
active subscriptions, and query that cache while answering a question.

MCP is ideal for exploration and debugging. Once the capability belongs in a
product, install its exact package and use the generated SDK.

## Sessions: application composition

A session composes several stacks and programs while sharing authentication,
chain reads, wallet access, and transaction transports. Generated packages
retain their own exact identities and bindings.

```ts
const session = await createSession({
  stacks: { markets: MARKETS_STACK },
  programs: { token: SPL_TOKEN_PROGRAM },
});

session.stacks.markets.views;
session.programs.token.accounts;
session.chain;
```

## Custom views

When an existing view does not answer the application question, define a new
read model with the advanced Rust authoring path.

Compilation produces definitions; deployment attaches hosted capabilities.
After deployment, query the result through MCP, refine it, and install the
finished stack into the application.

## Public contracts versus implementation

Applications should depend on:

- catalog capability metadata;
- exact descriptors and artifact identities;
- generated SDK types;
- documented query and transaction semantics; and
- explicit authentication scopes.

They should not depend on internal service names, deployment grouping, storage
layout, compiler processes, or inferred endpoint conventions.
