title: Actions
description: The actions an agent can run in a sandbox (call, invoke and withdraw), how to swap with invoke, how to preview them, and how to run each exactly once.
---

An agent changes a sandbox's wallet through exactly one tool,
`sandbox_invoke`, with one of three actions: `call`, `invoke` or `withdraw`.
Each needs a [grant](/sandboxes/agents/#grants) (a `call` runs under the
`invoke` grant), and each can be previewed first with `sandbox_preview`,
which takes the same arguments.

The loop is: **discover → preview → invoke.**

1. `sandbox_status` and `sandbox_rules`: what the wallet holds, which actions
   this agent holds, and which programs, instructions and functions are
   allowed.
2. `sandbox_derive`, when the action needs an address: a PDA (computed
   locally, with no network call) or an associated token account. To find
   the account an action starts from (a pool, a pair, a reserve) by the
   addresses it holds, use `sandbox_find_accounts`.
3. `sandbox_preview`: a dry run. Returns `pass` with what the wallet would
   lose and the transaction it built, or the refusal.
4. `sandbox_invoke`: runs it.

Without a stdio MCP server, the same loop runs in one-shot CLI commands:
`a4 sandbox status` and `a4 sandbox rules show`, then `a4 sandbox preview`
and `a4 sandbox invoke` with one action:

```bash
a4 sandbox preview --call <program> <function> --input <json|@file>
a4 sandbox preview --invoke <json|@file>
a4 sandbox preview --withdraw <lamports>
```

They send the same actions through the same client as the tools and return
the same results and refusals (`--json` prints them as the tools do). See
[`a4 sandbox`](/cli/commands/#a4-sandbox).

Pass u64 amounts as decimal strings.

## call

A function a program offers: `sandbox_rules` lists them per program as
`functions` (`name`, `summary` and `input`). Arete plans the whole instruction
sequence (account setup, refreshes, wrapping SOL), fills the sandbox wallet
and the accounts, and checks the result like any other action. When a
program lists a function for what you want to do, prefer `call` to
hand-assembling an `invoke`: a Kamino Lend deposit, for example, needs
reserve, obligation and farm refreshes in exact positions, and the function
gets them right.

```json
{
  "action": "call",
  "args": {
    "program": "KLend2g3cP87fffoy8q1mQqGKjrxjC8boSyAYavgmjD",
    "function": "transactions.obligation.deposit",
    "input": { "reserve": "<reserve>", "amount": { "ui": "0.1" } }
  }
}
```

### Function inputs

Each function's `input` describes the `input` a `call` takes, so you never
have to guess it:

```json
{
  "name": "transactions.obligation.withdraw",
  "summary": "Withdraw collateral from an obligation, in liquidity units or 'max'",
  "input": {
    "fields": [
      { "name": "owner", "type": "pubkey", "required": false, "fill": "wallet",
        "description": "The obligation owner; signs" },
      { "name": "reserve", "type": "pubkey", "required": true,
        "description": "The reserve to withdraw from" },
      { "name": "amount", "type": "amount", "required": true,
        "units": "the reserve's liquidity mint",
        "values": [{ "value": "max", "meaning": "the whole deposit" }],
        "description": "Liquidity to withdraw" },
      { "name": "payer", "type": "pubkey", "required": false,
        "description": "Pays for created accounts; defaults to the owner" }
    ],
    "unknownFields": "refused"
  }
}
```

| Key             | Meaning                                                                                                   |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| `name`          | The field, as `input` names it                                                                            |
| `type`          | `pubkey`, `amount`, `bool`, `string`, an integer width (`u8`, `i32`, `i64`), or `enum`                    |
| `required`      | Whether the call needs it                                                                                 |
| `fill`          | `wallet`: the sandbox wallet. Leave it out; any other address there is refused                            |
| `description`   | What the field is, and its default when the default depends on other fields                               |
| `units`         | For an `amount`: the token a `ui` amount is in                                                            |
| `default`       | The value used when the field is left out                                                                 |
| `values`        | Literals the field takes besides its type, each with its `meaning` (`"max"` on Kamino withdraw and repay) |
| `variants`      | For an `enum`: the strings it takes                                                                       |
| `unknownFields` | `refused` (a field the schema does not list is an error) or `ignored`                                     |

An `amount` is `{ "ui": "1.5" }` in whole units of its `units` token,
`{ "raw": "1500000" }` in base units, or a bare integer (base units). A bare
decimal string such as `"0.1"` is refused. A function listed without `input`
(an older server) is described only by its summary. `a4 sandbox rules show`
prints each function as a signature, such as
`transactions.obligation.withdraw(reserve: pubkey, amount: amount | "max", payer?: pubkey)`.

A function the rules do not allow is refused with
`sandbox-function-not-allowlisted`; its `allowedFunctions` lists the ones
they do. Input that does not match the schema is refused with
`sandbox-function-input-invalid`.

A function may also list `instructions`, the program's instructions it
builds for every input, and `innerInstructions`, the ones those make as
inner instructions (a CPI), such as the program's own log or event
self-CPI: an ORE deploy emits its event as a self-CPI of `log`. The rules
must allow each one, at any depth, so `sandbox_rules` adds
`missingInstructions` to a function that needs one they do not allow. A
call to it is refused with `sandbox-function-instruction-not-allowlisted`
before anything is planned; only the owner can allow the instruction, so
use another function, or an `invoke` of instructions the rules allow,
until then. An inner instruction the guard refuses is named in the
refusal (`instruction`), with a `hint` saying what the owner allows.

SPL Token, Token-2022 and the System program are on the sandbox's baseline
(`baseline` in `sandbox_rules`) for account plumbing such as wrapping SOL,
but the baseline grants none of their functions. A function of one of them
that the rules do not list is refused with `sandbox-function-not-allowlisted`
and `allowedFunctions: []`; its `grant` names the program, the function and
the instructions the owner adds to allow it. A program with no such function
answers `sandbox-function-not-installed`: send the instruction itself as an
`invoke`.

| Argument                        | Meaning                                                      |
| ------------------------------- | ------------------------------------------------------------ |
| `program`                       | The program id                                               |
| `function`                      | The function, named as `sandbox_rules` lists it              |
| `input`                         | The function's JSON input; the wallet member can be left out |
| `computeUnitLimit`              | Optional compute budget                                      |
| `computeUnitPriceMicroLamports` | Optional priority fee, per compute unit                      |
| `transactionFormat`             | `"v1"` (default) or `"v0"`                                   |

The result has the same shape as an `invoke` result, plus `plan`: the
`function`, `program`, `extension`, `pinnedSlot` and `fees` it was built
from.

## invoke

Named instructions of the programs your rules enable, encoded from each
program's IDL. One to 32 instructions per action, named exactly as
`sandbox_rules` lists them, as long as they fit one transaction: 4096
bytes and 64 accounts for v1 (the default), 1232 bytes for v0. A flow
that needs its setup, refreshes and the action together, such as a
first lending deposit, goes in one action. The sandbox wallet is the
only signer.

```json
{
  "action": "invoke",
  "args": {
    "instructions": [
      {
        "program": "Pump.fun",
        "instruction": "buy",
        "args": { "...": "as sandbox_rules lists them" },
        "accounts": { "...": "only those without a fill" }
      }
    ],
    "computeUnitPriceMicroLamports": "1000"
  }
}
```

| Argument                        | Meaning                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------ |
| `instructions[]`                | `{ program, instruction, args?, accounts?, remainingAccounts? }`               |
| `remainingAccounts`             | `[{ address, writable? }]`, for instructions that take a variable account list |
| `computeUnitLimit`              | Optional compute budget                                                        |
| `computeUnitPriceMicroLamports` | Optional priority fee, per compute unit                                        |
| `transactionFormat`             | `"v1"` (default) or `"v0"`                                                     |

Accounts with a `fill` in `sandbox_rules` can be left out: Arete fills
fixed addresses, the wallet, PDAs, token programs, your associated token
accounts and fields it reads from the accounts you give (a pool's mints and
vaults). A request still missing accounts is refused with
`sandbox-intent-invalid`, `missingAccounts`, and `accountGuidance` that
says how to find each one. See [Finding accounts](/sandboxes/accounts/).

## Swaps

There is no separate swap action. A swap is an `invoke` of the instructions
that make it, so it passes the same rules, limits and checks as any other
instruction:

1. **Resolve the venue.**
   - **A venue's own instructions**, when you know the pool: for example
     PumpSwap (pump-amm) `buy` and `sell` for a coin that has left its
     Pump.fun bonding curve, Pump.fun `buy` and `sell` on the curve, or a
     DEX's own swap instruction (Orca Whirlpool, Raydium, Meteora). This is
     the simplest path.
   - **A Jupiter route**, when you want the best route across venues: quote
     with Jupiter's Swap API, then ask it for `/swap-instructions` with the
     sandbox wallet as the user. Ask the quote for about 50 `maxAccounts`, so
     the route fits a v1 transaction (64 accounts, no lookup tables). The
     route only fills through venues whose programs your rules enable.
2. **Write the `invoke`.** Name each instruction as `sandbox_rules` lists it
   (Jupiter's swap is one of the Jupiter instructions there, such as
   `route_v2` or `shared_accounts_route_v2`), with its `args` decoded from
   the instruction data by the IDL types `sandbox_rules` gives, its named
   accounts, and any further accounts the route passes in
   `remainingAccounts`. Setup Jupiter returns, such as creating a token
   account or wrapping SOL, is baseline plumbing: put it in the same action,
   in order.
3. **`sandbox_preview`** with `action: "invoke"` until it passes, then
   **`sandbox_invoke`** with the same arguments.

```json
{
  "action": "invoke",
  "args": {
    "instructions": [
      {
        "program": "PumpSwap",
        "instruction": "sell",
        "args": { "...": "as sandbox_rules lists them" },
        "accounts": { "...": "only those without a fill" }
      }
    ]
  }
}
```

Tokens the sandbox bought may always be sold, through any route the rules
allow.

## withdraw

SOL to your wallet, the only destination a withdraw can have.

```json
{ "action": "withdraw", "args": { "lamports": "500000000" } }
```

## Transaction format

Actions build Solana v1 transactions (SIMD-0385) by default: up to 4096 bytes
and 64 accounts, no address lookup tables, with the compute budget in the
message itself. `transactionFormat: "v0"` builds the older format instead (up
to 1232 bytes). A transaction too large for its format is refused with rule
`transaction-size`.

## Exactly once

Every `sandbox_invoke` has an idempotency key: the agent's own
(`idempotencyKey`, 1 to 128 characters) or a generated one, returned on
success and on error. A key never runs twice.

- **The same request, the same key**: safe to send again. It returns the
  original result, success or refusal, in the same shape plus
  `replayed: true`. An action still in flight returns its current status. A
  replayed refusal also carries the record's `rejectCode`, which can differ
  from its `code`: go by the replayed `code` and `retryable`. A replayed
  outage is `retryable: true`, not a permanent refusal; retry it with a new
  key. See [Errors and refusals](/sandboxes/errors/).
- **A different request, a used key**: refused, not retryable, with the id of
  the action that has the key (`sandbox-duplicate-action`, or
  `sandbox-idempotency-key-reused`). Use a new key.

After a timeout, the action may have run, so never retry it under a new key.
Retry with the same key, or look it up first:

1. `sandbox_action` with the `idempotencyKey`.
2. If it ran, don't repeat it. If it was refused, retry with a new key. If no
   action has the key, retry with the same key.

Older servers answer every repeat of a key, the same request included, with
`sandbox-duplicate-action` and the action's id; look it up with
`sandbox_action` for its result.

## Results

A landed action returns its id, status, signature and `outflowLamports`:
everything that left the wallet, the network fee included.
`networkFeeLamports` is the network fee alone, null until the landed
transaction is read. `feeLamports`, when present, is something else: the
protocol's own fees. It also names the `guardPipeline` that checked it, such
as `execute-v1`. `sandbox_action` lookups and history items carry
`outflowLamports`, `networkFeeLamports` and `guardPipeline` too (not
`feeLamports`), and previews carry `outflowLamports` and `guardPipeline`.
`guardPipeline` is null or absent on actions recorded before it was kept and
on actions that never reached the guard, such as a rejected one. The full record (decoded
instructions, events, balance changes) is in the
[history](/sandboxes/history/). A refusal is a tool error with `code`,
`rule`, what triggered it, `retryable` and a `hint`; see
[Errors and refusals](/sandboxes/errors/).

### Preview results

A passing preview also says what the transaction does with rent:

- `newAccounts`: accounts it creates and leaves open, and `closedAccounts`:
  accounts it closes. Each is `{ address, owner, space, rentLamports }`. A
  wrapped-SOL account counts its rent reserve, not the SOL in it.
- An account the transaction creates and closes again, such as the
  temporary wSOL account of a native SOL swap or deposit, is in
  `closedAccounts` with `temporary: true` and the rent it held, and is not
  in `newAccounts`.
- `newAccountRentLamports` totals `newAccounts`.
  `closedAccountRentLamports` totals the closed accounts that existed
  before the transaction. A temporary account's rent comes back in the same
  transaction, so neither total counts it.
- `outflowParts` splits the outflow into `principalLamports` (the SOL the
  action itself moves), `rentLamports` (new rent less rent refunded),
  `networkFeeLamports` and `areteFeeLamports`. The four add up to the
  negated `walletLamportsChange`, and each is negative when SOL comes back.

`principalLamports` is what the program actually took. A lending deposit
can take slightly less than the amount asked, because the program deposits
only liquidity that mints whole collateral tokens: a lamport or so stays in
the temporary wSOL account, and its close returns it.

A `call` the API refused while checking it, previewed or run, says how far
it got:

- `stages`: each stage it passed, in order (`request`, `plan`, `rebuild`,
  `fees`, `build`, `check`, `guard`), then the one that refused it with its
  `code` and `reason`. `failedStage` names that stage.
- `plan`: the call's plan as far as it got, with the planned
  `instructions` once the function planned.
- `guardPipeline`: the pipeline that ran, or for a refusal before the
  guard, the one that checks this sandbox. `stages` says whether it ran.
- `walletLamportsChange` and `outflowLamports` when the guard's trial ran
  before refusing.

A passing preview lists no `stages`. An error before the API checks the
call, such as `sandbox-api-unreachable` or no sandbox chosen, has none of
these fields; its `code` and `hint` say what went wrong.
