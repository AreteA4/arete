:::caution[Alpha]
Sandboxes are in public alpha. They hold real SOL and tokens. Fund a sandbox
only with what you are prepared to lose, and expect the rules format, the API
and these docs to change.
:::

A sandbox is a hosted Solana wallet that an agent can use but never holds the
key to. You, the owner, create it, fund it, choose which programs it may use
and sign those rules once. The agent asks Arete to run actions; Arete builds
each transaction, checks it against your rules, signs it and sends it. The
agent never sees a private key, a transaction to sign or an RPC URL.

**The boundary is the wallet.** Whatever you send into the sandbox is the
agent's to use within the rules: it may trade it, and it may lose it. The
rules make sure the agent uses the programs you turned on, in the ways they
allow, and that funds cannot leave to somewhere you cannot recover them from.

## Set one up

1. On the [Sandboxes page](https://app.arete.run/dashboard/sandboxes) of the
   dashboard, create a sandbox and send SOL to its wallet address.
2. Build its rules: turn on the supported programs the agent may use, set
   options for each, add any addresses funds may go to, and sign once.
3. Grant your agent access. The agent uses its own account's API key; it
   never gets yours.
4. Give the agent the sandbox id and run the Arete MCP server:

```bash
export ARETE_SANDBOX_ID=<sandbox id>
export ARETE_API_KEY=<the agent account's secret key>   # or `a4 login` as the agent
a4 mcp
```

The [MCP server](/agent-skills/mcp/) then lists the `sandbox_*` tools:
`sandbox_status`, `sandbox_rules` and `sandbox_derive` to look around,
`sandbox_preview` for a dry run, `sandbox_invoke` to run an action (the only
tool that moves funds), `sandbox_action` to look one up, and the read-only
`sandbox_history` and `sandbox_holdings`.

## Rules (version 3)

The rules builder generates this document for you to sign:

```json
{
  "version": 3,
  "programs": [
    {
      "programId": "6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P",
      "name": "Pump.fun",
      "enabled": true,
      "instructions": ["buy", "sell"],
      "spendLimit": { "lamports": "1000000000", "windowSeconds": 86400 }
    }
  ],
  "transferAllowlist": ["<an address you control>"]
}
```

| Field               | Meaning                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------ |
| `programs[]`        | The supported programs, each turned on or off with `enabled`                                           |
| `instructions`      | Optional. The instructions allowed for that program; left out, the registry's safe set for it          |
| `spendLimit`        | Optional. The most SOL, in lamports, the sandbox may spend through that program per `windowSeconds`    |
| `transferAllowlist` | Addresses funds may be sent to besides your own wallet (always allowed) and the sandbox's own accounts |

Check a rules file before you sign it. Nothing is sent anywhere:

```bash
a4 sandbox rules validate rules.json
```

```text
rules.json: valid Rules v3 (enabled: Pump.fun)
```

Misspelt keys are errors (`spend_limit` would otherwise be signed and
ignored), as are program ids and addresses that are not base58 Solana
addresses and limits of zero. Version 1 and 2 documents are reported as the
earlier format. Passing locally does not guarantee the API accepts every
program: it must also be one the registry supports.

## What is enforced

- **Only enabled programs and their allowed instructions**, checked in every
  instruction of the transaction and in the calls those programs make.
- **Where funds may go.** SOL and tokens may leave the enabled programs only
  to your wallet, an address on your `transferAllowlist`, or the sandbox's own
  accounts. A transfer anywhere else is refused.
- **Per-program spend limits**, when you set them.
- **Exits are always allowed.** The agent may always sell or exit a token the
  sandbox bought, at a loss too.
- **No key handover.** Authority and delegate changes on the sandbox's
  accounts are refused, and the agent never receives a key or a transaction
  to sign.
- **Grants.** Only agents you granted can mint a token for the sandbox, and
  only for the actions you granted. Revoking a grant stops the agent at its
  next call.
- **Every action is recorded**, refusals included, and readable as history.

A refusal names its `code`, the `rule` that refused and what triggered it, so
an agent can correct the request instead of guessing. Every error also says
whether the same request may succeed later (`retryable`) and what to do
(`hint`): a wallet that cannot pay is refused with
`sandbox-guard-insufficient-funds` and its balance, not as a failure to
retry.

## What is not enforced yet

- **Trade quality.** The rules decide where funds may go, not whether a trade
  is a good one. Price, slippage within what you allowed, and losses are the
  agent's to manage.
- **Per-token limits.** Purchases are tracked per mint, but there is no limit
  per token yet. Use per-program spend limits.
- **Global caps.** Version 3 rules have no sandbox-wide per-action or
  per-window caps. The per-program spend limit replaces them.
- **Decoded positions.** Lending and liquidity positions show as labeled raw
  accounts, not as decoded balances.

## History and holdings

The agent, and you through the CLI, can read every action the sandbox ran and
what it holds now. Both are read-only.

```bash
export ARETE_SANDBOX_ID=<sandbox id>
a4 sandbox history                         # newest first, 20 per page
a4 sandbox history --status landed --since 24h
a4 sandbox history --program Pump.fun --all --json
a4 sandbox holdings
a4 sandbox rules show
```

```text
Sandbox 6f1c2c43-6d3c-4a51-9b8e-0e3c1e2a7b10  history, newest first

  2026-11-12 10:00:00  landed    Pump.fun.buy  -0.105005 SOL, +1234.5 7xKX…gAsU  5Kt3…6uHq
      events: TradeEvent ×2
  2026-11-12 09:58:30  rejected  Pump.fun.sell
      sandbox-guard-trial-failed

More: a4 sandbox history --cursor eyJpZCI6ImEyIn0
```

Each action has its time, status, the programs and decoded instructions,
the Anchor events the programs emitted (decoded against each program's IDL;
an event that does not decode keeps its bytes and the reason), the SOL and
token changes, the accounts it touched and, with `--raw` or the
MCP tool's `includeRaw`, the parsed transaction with its balances before and
after. Holdings list SOL, each token with `acquiredBySandbox` for tokens the
sandbox bought, and program positions.

The filters (`--status`, `--program`, `--mint`, `--since`) are applied by
the client to the pages it reads. A filtered read keeps reading pages until
enough actions match (up to 10 pages per call), then prints the cursor to
carry on from.

## Caveats

- **Real funds.** Anything in the sandbox may be traded away. Withdraw what
  you want to keep.
- **The rules are yours to get right.** An address on the allowlist can
  receive any amount. Allow only addresses you control.
- **Alpha limits.** Few programs are supported at first, requests are rate
  limited, and the API and rules format may change before general
  availability.
- **History detail.** Actions from early in the alpha may show fewer details
  than newer ones.
